Отправить конкретную версию проекта на свой сервер и вернуть предыдущую, если проверка после установки завершилась ошибкой. В ungit команда `push` запускает этот путь целиком: от снимка файлов до выпуска релиза.

Инструмент рассчитан на небольшие self-hosted проекты. Он хранит объекты, индекс, деревья и коммиты локально; серверный агент принимает пакет, проверяет его и выполняет сценарии развёртывания. Git-сервер для этого не нужен.

```
ungit init        # create .ungit/ in the project
ungit add .       # hash files into the index
ungit push master -c "initial deploy"  # commit + delivery to configured core
ungit log / status / remote
```

## Что здесь можно оценить

Модель версий связана с жизненным циклом релиза: после deploy-скриптов агент запускает `health.sh` и при ненулевом коде завершения откатывается к предыдущему релизу. Это пример собственной CLI-утилиты с серверной частью и явным протоколом доставки.

Python-код использует стандартную библиотеку. CLI передаёт архив в core по HTTP, агент забирает его по заданию из очереди. Постоянно работающий клиентский демон не требуется.

Обсудить похожий проект: [sh3l.beer](https://sh3l.beer).

## Компоненты

| Пакет | Назначение |
|---|---|
| `core/` | модель объектов, пользователи и bearer-токены, репозитории, ссылки, пакеты, задания и протокол CLI ↔ агент |
| `storage/` | локальное хранилище `.ungit/`: объекты, ссылки и индекс |
| `cli/` | команда `ungit` |
| `agent/` | приём, проверка и выпуск релиза, deploy-скрипты, health-check и откат при ошибке; релизы хранятся в `/opt/ungitted` |

В `core/` также есть адаптер [croc](https://github.com/schollz/croc). Основной сценарий CLI → core → agent работает по HTTP и не требует установки croc.

## Этапы развёртывания

Агент выполняет скрипты из доставленного архива. Между `ship.sh` и `postship.sh` он переключает ссылку `current` на новый релиз:

```
.ungit/deploy/preship.sh
.ungit/deploy/ship.sh
.ungit/deploy/postship.sh
.ungit/deploy/health.sh    # non-zero exit → rollback to the previous release
```

## Установка

Нужны Linux, Python 3.12+ с модулем `venv` и доступ к PyPI для установки сборочных зависимостей. Установите комплект на машину разработчика, core и агент; для локальной проверки достаточно одной машины.

```bash
./install.sh
export PATH="$PWD/.venv/bin:$PATH"   # текущий терминал
ungit --help
ungit-core --help
ungit-agent --help
```

Установщик создаёт `.venv`, устанавливает четыре пакета и добавляет PATH в `.zshrc` или `.bashrc` согласно `$SHELL`. Повторный запуск не дублирует строку. `VENV`, `PYTHON` и `RC_FILE` позволяют указать другие пути; прежний `BASHRC` тоже поддерживается. Перемещение checkout после editable-установки требует повторного запуска установщика.

## Первый деплой локально

**1. Запустите core.** Первая команда выдаст токен пользователя. Данные core по умолчанию находятся в `~/.local/share/ungit/core`.

```bash
ungit-core user create owner --admin
ungit-core serve --host 127.0.0.1 --port 8765
```

**2. В другом терминале создайте проект и настройте доставку.** Замените `<USER_TOKEN>` выданным токеном. Команда регистрации агента выдаст отдельный `<AGENT_TOKEN>`.

```bash
mkdir -p /tmp/ungit-demo
cd /tmp/ungit-demo
ungit init
ungit login --core-url http://127.0.0.1:8765 --token '<USER_TOKEN>'
ungit remote add origin http://127.0.0.1:8765/demo
ungit agent register local-agent
ungit pipeline add local-agent
printf 'v1\n' > app.txt
cat > .ungit/deploy/health.sh <<'SH'
#!/bin/sh
test -f "$UNGIT_RELEASE/app.txt"
SH
ungit add .
ungit push master -c "first release"
```

`push` создаёт commit и ставит задания в очередь. Сообщение `queued` означает, что core принял доставку; оно ещё не подтверждает успешный деплой. С `--wait` команда дожидается результата: печатает стадии, при ошибке — хвост лога упавшей стадии, и выходит с кодом 1. Без настроенного remote команда сохраняет только локальный commit.

**3. В третьем терминале запустите агента.** В локальном примере используем доступный пользователю runtime-каталог. Значение по умолчанию для сервера: `/opt/ungitted`.

```bash
export UNGIT_AGENT_TOKEN='<AGENT_TOKEN>'
ungit-agent run --name local-agent --core-url http://127.0.0.1:8765 \
  --root "$HOME/.local/share/ungit/agent"
```

После `[deploy] success` файл доступен через `~/.local/share/ungit/agent/projects/demo/current/app.txt`. Для обработки одного задания с выходом используйте `--once`: успешная обработка или пустая очередь возвращают `0`, ошибка задания возвращает `1`. Постоянный агент после ошибки продолжает опрашивать очередь.

Для разных машин core и агент запускаются отдельно, а `remote` и агенту задаётся доступный адрес core. Передача bearer-токенов между машинами требует защищённого соединения, например HTTPS через reverse proxy. Этот раздел проверен с локальным HTTP на `127.0.0.1`.

## Обновление и откат

В каталоге проекта:

```bash
printf 'v2\n' > app.txt
ungit add .
ungit status
ungit push master -c "second release"
ungit log master
```

`add` сохраняет содержимое файлов и исполняемый бит в локальные объекты. Последующие изменения рабочей папки не меняют снимок для `push`. Удаление учитывается в выбранной области: `add .` обновляет весь индекс, `add app/` только этот каталог, `add deleted.txt` фиксирует удаление ранее добавленного файла. `status` сравнивает рабочую папку с индексом.

Скрипты `.ungit/deploy/*.sh` считываются при `push` и входят в проверяемый архив доставки. На сервере агент сверяет хеш архива, commit, дерево файлов и реквизиты задания. Повторная доставка уже активного commit не запускает скрипты заново и не очищает релиз.

Для ручного отката выполните на машине агента:

```bash
ungit-agent rollback demo --root "$HOME/.local/share/ungit/agent"
```

Команда меняет местами `current` и `previous`. До второго успешного релиза предыдущей версии нет, поэтому ручной откат завершится понятной ошибкой. Деплой и ручной откат одного проекта используют общую файловую блокировку.

При ошибке `preship` или `ship` действующая версия остаётся на месте. Ошибка `postship` или `health` восстанавливает обе ссылки до состояния перед деплоем, сохраняя историю рабочих версий. Если упал первый деплой, активной ссылки не остаётся. Вывод скриптов и события пишутся в `projects/<project>/logs/deploy-<job_id>.log`, состояние находится в `state.json`.

## Границы текущего цикла

- Обновляйте CLI, core и agent вместе. После перехода со старой версии выполните `ungit add .`: старые индексы содержат хеши без сохранённого содержимого файлов.
- В доставке поддерживаются обычные файлы с режимами `0644` и `0755`. Символические и жёсткие ссылки в архиве отклоняются; владелец, ACL и произвольные Unix-права не переносятся.
- Служебные каталоги, state-файл, lock-файл и логи внутри runtime не должны быть symlink. `current` и `previous` могут указывать только на каталог релиза того же проекта. Сам `--root` разрешается в абсолютный путь при запуске.
- Автоматически игнорируются `.ungit`, `.git`, `node_modules`, `.venv`, `__pycache__` и `*.pyc`. Дополнительные шаблоны читаются из `.ungitignore` в корне проекта: строка без `/` совпадает с именем файла или каталога на любом уровне (`.env.prod`, `*.log`), строка с `/` сопоставляется с путём от корня (`/deploy/*.yml`), `#` начинает комментарий. Отрицание `!` и `**` не поддерживаются, `.gitignore` не читается. Игнорируемый файл не попадает в индекс даже при явном `ungit add <путь>`, а после `ungit add .` выпадает из индекса. Файлы `.env` без шаблона не исключаются: секреты храните на сервере вне релиза.
- Один процесс core обслуживает свой каталог данных; запускайте один рабочий цикл на identity агента. Задания выдаются в порядке push. После аварийного завершения процесса уже захваченное задание автоматически в очередь не возвращается; для повторной доставки создайте новый push.
- Каждый deploy-скрипт ограничен 300 секундами. При превышении завершается его группа процессов; для `postship` и `health` затем выполняется откат. Скрипты исполняются с правами пользователя агента, без песочницы ОС.
- Откат переключает файловые ссылки. Изменения БД, внешних сервисов и содержимого `shared/` он не отменяет. Перезапуск приложения должен учитывать выбранную вами схему развёртывания.

## Проверки

```bash
.venv/bin/python -m pip install pytest
.venv/bin/pytest -q
```

Тесты включают реальный локальный core, установленные CLI и HTTP-приложение, которое обслуживает `current`: последовательные релизы, staged-содержимое, удаление файла, HTTP health-check и ручной откат. Ответ приложения проверяется после обновления и обоих видов отката. Для этого среда должна разрешать loopback-сокеты. Отдельный HTTP-тест проверяет все обязательные маршруты и границы доступа пользователей и агентов. Остальные проверки покрывают целостность доставки, очередь, таймауты, runtime-пути и сохранение истории релизов.

Контракт каждого пакета описан в его `AGENTS.md`.
